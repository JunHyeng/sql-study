# 2단계 2강: JOIN 심화 (SELF JOIN, 행이 불어나는 함정, ON vs WHERE)

> 시니어의 한마디: "JOIN은 **오류 없이** 숫자를 망가뜨리는 1순위입니다. JOIN을 하나 붙일 때마다 **행 수가 어떻게 바뀌는지** 확인하는 습관이 실력입니다."

## 오늘의 목표

- 같은 테이블끼리 붙이는 **SELF JOIN**을 쓸 수 있다. (상사 이름, 추천인 이름)
- JOIN 후 **행이 불어나서(fan-out)** 합계가 부풀려지는 함정을 알아채고 피할 수 있다.
- LEFT JOIN에서 조건을 **ON에 둘 때와 WHERE에 둘 때**의 차이를 설명할 수 있다.

## 1. SELF JOIN: 같은 테이블을 두 번 쓰기

`employees`의 `manager_id`는 **같은 테이블의 `emp_id`**를 가리킵니다. 직원 이름 옆에 상사 이름을 붙이려면 `employees`를 **두 번** 불러서 각각 다른 별칭을 붙입니다.

```sql
SELECT e.name AS 직원,
       m.name AS 상사
FROM employees e                 -- e: 직원 역할
LEFT JOIN employees m            -- m: 상사 역할 (같은 테이블!)
       ON e.manager_id = m.emp_id;
```

- 테이블은 하나지만 **역할이 두 개**라고 생각하면 됩니다. 별칭이 없으면 어느 쪽 `name`인지 구분할 수 없습니다.
- 대표는 `manager_id`가 NULL이라 INNER JOIN이면 빠집니다. 모든 직원을 보려면 **LEFT JOIN**.

`customers.referred_by`(추천인)도 같은 구조입니다.

> [!TIP]
> 엑셀로 치면 같은 시트를 복사해서 "직원 시트"와 "상사 시트"로 두 개 띄워 놓고 VLOOKUP 하는 것과 같습니다.

## 2. 행이 불어나는 함정 (fan-out)

`orders`의 `coupon_amount`는 **주문 1건에 1번** 적혀 있습니다. 그런데 `order_items`와 JOIN하면?

| order_id | coupon_amount | (JOIN 후) order_item_id |
|---|---|---|
| 100 | 5000 | 201 |
| 100 | 5000 | 202 |
| 100 | 5000 | 203 |

상품을 3개 산 주문은 **3행으로 불어나고**, 쿠폰 5000원도 **3번 복사**됩니다. 이 상태에서 `SUM(o.coupon_amount)`를 하면 15000원이 됩니다.

```sql
-- ❌ 쿠폰 총액이 부풀려짐
SELECT SUM(o.coupon_amount)
FROM orders o
JOIN order_items oi ON o.order_id = oi.order_id
WHERE o.status = '배송완료';

-- ✅ 주문 단위 값은 주문 테이블에서만 집계
SELECT SUM(coupon_amount)
FROM orders
WHERE status = '배송완료';
```

### 규칙: "이 값은 어느 단위(grain)에 붙어 있나?"

| 값 | 단위 | 집계할 때 |
|---|---|---|
| `coupon_amount`, `shipping_fee`, 주문 수 | **주문** 1건당 1개 | `orders`에서, 또는 `COUNT(DISTINCT o.order_id)` |
| `unit_price × quantity`, 판매 수량 | **주문상세** 1줄당 1개 | `order_items`와 JOIN해서 |
| 고객 수 | **고객** 1명당 1개 | `COUNT(DISTINCT customer_id)` |

1단계 10강 B-2에서 `COUNT(DISTINCT)`로 피했던 바로 그 함정입니다. **단위가 다른 값을 한 쿼리에서 집계할 때** 생깁니다. (둘을 한 번에 깔끔하게 구하는 방법은 4강 서브쿼리에서 배웁니다)

> [!WARNING]
> fan-out은 **오류가 안 나고, 숫자가 그럴듯하게 커질 뿐**이라 가장 늦게 발견됩니다. JOIN을 붙인 뒤 `COUNT(*)`가 예상보다 커졌다면 의심하세요.

## 3. LEFT JOIN: 조건을 ON에 둘까, WHERE에 둘까

요청: "**모든 고객**의 12월 배송완료 주문 수 (없으면 0)"

```sql
-- ❌ WHERE에 오른쪽 테이블 조건 → 주문 없는 고객이 사라짐
SELECT c.customer_id, COUNT(o.order_id) AS 주문수
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.status = '배송완료'
  AND o.ordered_at >= '2025-12-01' AND o.ordered_at < '2026-01-01'
GROUP BY c.customer_id;          -- 300명이 아니라 87명만 나옴
```

LEFT JOIN으로 주문 없는 고객을 살려 놨는데(오른쪽이 NULL), WHERE에서 `o.status = '배송완료'`를 검사하면 **NULL은 참이 아니라서** 그 고객들이 다시 걸러집니다. 결과적으로 **INNER JOIN과 똑같아집니다.**

```sql
-- ✅ 오른쪽 테이블 조건은 ON에 → "붙일 주문을 고를 때" 적용
SELECT c.customer_id, COUNT(o.order_id) AS 주문수
FROM customers c
LEFT JOIN orders o
       ON c.customer_id = o.customer_id
      AND o.status = '배송완료'
      AND o.ordered_at >= '2025-12-01' AND o.ordered_at < '2026-01-01'
GROUP BY c.customer_id;          -- 300명, 주문 없으면 0
```

| 조건 위치 | 의미 | 결과 |
|---|---|---|
| `ON` | 오른쪽에서 **어떤 행을 붙일지** 고름. 못 찾으면 NULL로 남김 | 왼쪽 300명 전부 유지 |
| `WHERE` | JOIN이 끝난 결과에서 **행을 걸러냄** | NULL인 행이 사라짐 |

> [!TIP]
> 규칙: **LEFT JOIN의 오른쪽 테이블 조건은 ON에, 왼쪽 테이블 조건은 WHERE에.** (예외: 7번 "IS NULL로 없는 것 찾기"는 일부러 WHERE에 씀)

`COUNT(o.order_id)`를 쓴 이유도 중요합니다. `COUNT(*)`는 NULL로 채워진 행도 1로 세서 주문 없는 고객이 **0이 아니라 1**이 됩니다. (1단계 6강 COUNT 3형제, 10강 A-3)

## 4. 없는 것 찾기 (Anti Join) 복습

```sql
-- 한 번도 팔리지 않은 상품
SELECT p.name
FROM products p
LEFT JOIN order_items oi ON p.product_id = oi.product_id
WHERE oi.order_item_id IS NULL;
```

1단계 8강 7번(주문 없는 고객)과 같은 패턴입니다. 여기서는 **"짝이 없는 행"을 찾는 게 목적**이라 WHERE에 `IS NULL`을 씁니다.

## 5. JOIN 체크리스트 (실무용)

1. JOIN 하기 **전** 왼쪽 테이블 행 수를 안다.
2. JOIN 하고 **후** 행 수를 본다. 늘었다면 1:N 관계라서 정상인지, 의도치 않은 fan-out인지 판단한다.
3. 집계하는 값의 **단위**(주문? 상세? 고객?)를 확인한다.
4. LEFT JOIN이면 오른쪽 조건이 WHERE에 있지 않은지 본다.
5. 테이블 별칭을 붙이고 모든 컬럼에 `별칭.컬럼`을 쓴다.
